---
title: Migration drift / SQLITE_MISMATCH
description: When the dev DB schema doesn't match what your code expects.
---

## Symptoms

- A query that worked yesterday now throws `SQLITE_MISMATCH: datatype mismatch`
- The form 500s with a Drizzle error mentioning column types
- `_hub_migrations` table is missing rows you expect to see
- After switching branches, things stop working in confusing ways

## Diagnosis

```bash
# Compare what migrations the DB thinks are applied:
sqlite3 .data/db/sqlite.db "SELECT name FROM _hub_migrations;"

# vs what's in the journal (the source of truth):
cat server/db/migrations/sqlite/meta/_journal.json | grep '"tag"'
```

If they differ, you have drift.

## Common cause: orphan hand-written migrations

Earlier in the project's history there were SQL files in `server/db/migrations/sqlite/` that were **not** tracked in `meta/_journal.json` — for example `0003_rename_tijdstip_to_time_slot.sql` and `0004_add_role_to_users.sql`. `@nuxthub/core` runs every `.sql` file in the folder, so these ran and tried to apply changes that the proper drizzle-generated migrations had already covered. Conflict → migration fails → DB state becomes inconsistent.

These have been cleaned up, but if it happens again:

1. Identify the orphan: any file in `server/db/migrations/sqlite/*.sql` whose name doesn't appear in `meta/_journal.json` under `entries[].tag`
2. Delete the orphan from both `server/db/migrations/sqlite/` AND `.data/db/migrations/sqlite/` (the runtime copy)
3. Wipe and rebuild the DB (next section)

## Common cause: switching branches mid-development

If you're on a feature branch with new migrations, then switch to `main` which doesn't have them, your local DB has applied things that don't exist in the schema anymore. The fix is the same — wipe and rebuild.

## Fix: wipe and rebuild

```bash
# Stop dev server first (Ctrl+C)

# Wipe the local DB
rm -f .data/db/sqlite.db .data/db/sqlite.db-shm .data/db/sqlite.db-wal

# Restart — @nuxthub/core re-applies migrations from scratch
pnpm run dev

# Re-seed the superadmin
curl -k -X POST https://localhost:3000/api/seed
```

You lose any data in `.data/db/sqlite.db` (form submissions, additional users you created) but the schema is guaranteed to match the current branch.

## Prevention

- **Always use `pnpm run db:generate`** to create new migrations — never hand-write SQL files
- **Don't rename existing migrations** — once a migration is in the journal and someone has applied it, treat its file as immutable
- **When in doubt, wipe the local DB** — it's cheap

## Production migration safety

Production D1 follows the journal religiously — `@nuxthub/core` only applies migrations whose name isn't in `_hub_migrations`. So orphan files in the local repo don't pollute production unless they're committed AND survive past the next deploy.

If production migrations get drift (e.g. someone ran `wrangler d1 execute` to hand-modify the schema), it's much harder to fix safely. Don't.
