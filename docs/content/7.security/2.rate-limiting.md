---
title: Rate limiting
description: Per-route rate limits for API endpoints.
---

## Config

Rate limiting is disabled globally and applied only to `/api/*` via `routeRules`:

```ts [nuxt.config.ts]
routeRules: {
  '/api/*': {
    security: {
      rateLimiter: {
        tokensPerInterval: 10,
        interval: 60_000  // milliseconds
      }
    }
  }
}
```

This permits **10 requests per minute per IP** for any URL under `/api/`. Requests beyond the limit get a `429 Too Many Requests` response.

## Why per-route, not global

A global rate limiter applied to every page would block legitimate browsing (each page navigation pulls multiple `_nuxt/` chunks, images, etc.). API endpoints are the high-value attack surface — login bruteforce, form spam — so they're the only routes that need it.

## What's NOT rate-limited (intentionally)

- Static asset requests (`/_nuxt/*`, `/assets/*`)
- Nuxt Content endpoints (`/__nuxt_content/*`)
- Nuxt Studio endpoints (`/__nuxt_studio/*`)
- Page routes (`/nl/*`, `/fr/*`, `/dashboard/*`)
- OG image generation (`/__og-image__/*`)

## Tuning

If you find legitimate use cases hitting the limit (e.g. a typeahead search that fires per keystroke), either:

1. **Move the endpoint outside `/api/*`** (e.g. to `/server/*`) — won't be rate-limited
2. **Increase the limit** for that specific path:

   ```ts
   routeRules: {
     '/api/*': {
       security: { rateLimiter: { tokensPerInterval: 10, interval: 60_000 } }
     },
     '/api/search/**': {
       security: { rateLimiter: { tokensPerInterval: 60, interval: 60_000 } }
     }
   }
   ```

## How the limit is tracked

`nuxt-security` uses an in-memory LRU cache by default — counts are per-Worker-instance, not shared across Cloudflare's edge. In practice this still works: each visitor mostly hits the same edge location for the duration of their session.

For more rigorous rate limiting (shared state across all instances), you'd need to switch to a Redis or Cloudflare KV-backed driver. Not necessary at the current scale.

## Login bruteforce specifically

The login endpoint (`/api/auth/login`) is covered by the `/api/*` rule, so an attacker is throttled to 10 attempts per minute per IP. That's enough to brute-force a weak password — so:

- Enforce minimum password length (12+ chars) in `register.post.ts` and `reset-password.post.ts`
- Encourage password manager usage (long random passwords)
- For higher security, consider adding lower per-route limits on `/api/auth/login` specifically (e.g. 5 per minute)
