## The flow

1. **Edit** `server/db/schema.ts`
2. **Generate** a migration SQL file: `pnpm run db:generate`
3. **Apply** — happens automatically when you run `pnpm run dev` (handled by `@nuxthub/core`)

You don't write SQL by hand. Drizzle introspects the schema diff and produces the right `CREATE TABLE` / `ALTER TABLE` / etc. statements.

## What `db:generate` does

```bash
pnpm run db:generate
# → reads server/db/schema.ts
# → diffs against the last journal entry
# → writes a new file: server/db/migrations/sqlite/NNNN_random-name.sql
# → updates server/db/migrations/sqlite/meta/_journal.json
# → updates server/db/migrations/sqlite/meta/NNNN_snapshot.json
```

The journal (`meta/_journal.json`) is the source of truth for which migrations exist. `@nuxthub/core` reads it on dev start and applies any new ones.

## Inspecting migration history

```bash
sqlite3 .data/db/sqlite.db "SELECT name FROM _hub_migrations;"
# 0000_sloppy_doctor_octopus
# 0001_damp_blade
# 0002_moaning_raza
# ...
```

`_hub_migrations` is `@nuxthub/core`'s ledger of applied migrations. Compare this against the journal to spot drift.

## Never hand-write SQL files

::warning
**Don't manually create files in `server/db/migrations/sqlite/`.** `@nuxthub/core` reads every `.sql` file in that folder and runs it — but only `db:generate`-created files are tracked in the journal.

If you add an orphan SQL file, it runs, but the journal doesn't know about it. Other devs / CI / fresh installs end up in inconsistent states. The two-`0003`-prefix mess in this project's history (described in [Migration drift](/troubleshooting/migration-drift)) was caused by exactly this.
::

If you need to do something Drizzle can't express (e.g. a custom data backfill), generate an empty migration and write the SQL inside it — at least it'll be journaled.

## Resetting the dev DB

If the local DB gets into a confusing state (e.g. you switched branches with conflicting migrations, or `_hub_migrations` is out of sync):

```bash
# Wipe the local DB completely
rm -f .data/db/sqlite.db .data/db/sqlite.db-shm .data/db/sqlite.db-wal

# Restart dev — migrations re-apply from scratch
pnpm run dev

# Re-seed (creates the superadmin user)
curl -k -X POST https://localhost:3000/api/seed
```

You lose any data in the local DB but the schema is guaranteed fresh.

## Production migrations

In production (Cloudflare D1), migrations are applied on first deploy by `@nuxthub/core`. There's no manual `wrangler d1 migrations apply` step — NuxtHub handles it.

To peek at production migration state:

```bash
npx wrangler d1 execute DB --command "SELECT name FROM _hub_migrations;"
```

Add `--env preview` for the preview database.
